Artifact Server product and architecture proposal

Publish finished client-side websites and web applications, including multi-page static sites, compiled React, Vue, or Svelte applications, and prototypes written in HTML, CSS, and JavaScript. Also publish Markdown, text, JSON, source code, images, PDFs, audio, video, ZIP archives, and other files. Artifact Server stores the exact files and uses the browser's built-in display or download behavior. It does not build source code, run backend code, convert media, or provide specialized document viewers.

August 12, 2026 Product proposal Local, private network, server, Kubernetes, Cloudflare, AWS, GCP, Azure

Product summary

Proposed behavior, access, deployment, and scope.

Supported web content

Finished client-side sites and web applications whose runtime consists only of files served to a browser: HTML, CSS, JavaScript, images, and fonts. This includes multi-page static sites, single-page applications compiled from React, Vue, or Svelte, and prototypes written directly in HTML, CSS, and JavaScript. It also stores ordinary files such as images, video, PDFs, audio, text, and ZIP archives. It does not support an application that needs Node.js, Python, a database, a server function, or server-side rendering when a request arrives.

Who can open it

One installation is one closed group: one person or one team. 1. Account required. Only people admitted to that installation can open it. There is no public self-sign-up. 2. Public link. No account is required. Anyone who can connect to this Artifact Server and has the link can open the current version. History and comparisons still require an account. A public link does not put a private server on the internet.

What gets saved

For a website or web application, the server saves the complete directory of finished runtime files and the HTML file that opens first, usually index.html. Publishing again creates a new saved copy and never alters a previous copy. The server compares file lists and changed text without Git. Optional Git history is a second, private copy.

Agents

An agent publishes one actual file or one finished directory through normal web requests or MCP. It does not put raw HTML, CSS, JavaScript, or base64 file contents in an MCP or JSON argument. The publishing client handles the upload and returns an ID, version number, and link. A hosted MCP connection opens browser sign-in and approval the first time. Local and private installations can use local or server API keys.

Deployment

The same product rules run locally, on one server, on Kubernetes, or on Cloudflare. Official installers later cover AWS, GCP, and Azure without changing the product.

Not included

No comments, annotations, workspace collaboration, general-purpose source-code hosting, code-building service, arbitrary add-ons, or programs that must keep running on the server. Plannotator provides review and collaboration.

The product

Publishing workflow

An agent finishes a compiled web application, HTML prototype, or report and publishes it. A person opens the returned link. The agent can publish another version without changing the earlier one, and a person can compare the two versions.

No separate hosting project is created for each artifact. The server already owns the link, browser view, saved versions, comparisons, and sharing. It does not store comments or annotations.

Send one file or the complete directory of finished client-side files.

Open

Ask the agent to open it. A local artifact opens from the local server; a team artifact opens from that team's server.

Compare

See which files and text changed between any two saved versions.

Choose whether opening it requires an account.

The object

Artifact and version model

An artifact is one published item that keeps the same identity over time. It has a name, an owner, an access setting, optional tags, a link, and a history of saved versions.

An artifact is one item that can be published more than once.

Each intentional publish saves a new version. That saved version never changes. It contains one or more files and names which file should open first. A retry with the same request key returns the earlier result instead of creating another version. A one-file report and the finished output from a React project use the same model.

Artifact Server serves finished client-side files. It does not install packages, compile source code, start Node.js or Python, connect an artifact to a database, run server functions, or perform server-side rendering when a request arrives.

An artifact can have up to 20 optional tags. The server trims whitespace, normalizes Unicode and letter case, removes duplicates, and stores tags in a stable order. Each stored tag contains 1 to 40 user-perceived characters and no control characters. Tags apply to the artifact, not one saved version, so publishing or restoring does not change them. The first release supports exact tag filtering; it does not add tag categories, nested tags, or per-version tags.

How the server stores an artifact

The server stores six kinds of records:

  • Artifact: the same item over time, including its name, owner, access setting, optional tags, and current version.
  • Version: the saved copy created when someone publishes. It never changes and points to one manifest.
  • Manifest: the canonical, ordered list of file paths, fingerprints, sizes, media types, and the entry file.
  • File: one file in a version, including its name, folder path, file type, size, and SHA-256 fingerprint.
  • Source: an optional note about an upload, approved local import, or agent.
  • Action: who published, restored, changed access, changed tags, or deleted the artifact and when.

A SHA-256 fingerprint is calculated from a file's exact contents. If one byte changes, the fingerprint changes.

Paths are portable relative paths. The server rejects absolute paths, dot segments, .git path components, backslashes, null bytes, percent-encoded separators, symlinks, special files, duplicate normalized names, and names that collide only by case or Unicode normalization. The entry file must exist in the manifest.

The manifest is serialized in one fixed order and hashed. That manifest digest, not an operating-system directory walk or Git commit, is the portable identity of the saved file set and the basis for comparison and idempotency checks.

Customer experience

Supported content and publishing behavior

The product stays small enough to explain without a tour. Publishing, viewing, versions, and sharing make up the customer experience.

Use the browser's native file behavior

HTML opens as a website. Images, PDFs, audio, and video use the browser's normal controls. Text, JSON, Markdown, and source files open as plain text in the first release. ZIP archives and unknown file types download. Audio and video support byte-range requests so seeking works.

The first release does not convert media, generate thumbnails, extract ZIP files, render Markdown, highlight source code, or ship a custom PDF viewer. Supporting these file types adds routing, media-type, range-request, and download tests—not a separate processing service.

Serve complete client-side output directories

The server delivers the published directory without rebuilding it. Relative links between HTML, CSS, JavaScript, images, and fonts continue to work. The content may also load scripts, styles, images, and fonts from other websites.

If the published website or HTML report contacts another web service, that service must allow requests from other websites. A private network may block internet access. Artifact Server does not copy or replace files loaded from elsewhere.

Saved versions that do not change

Every new publish request creates a saved version. Once saved, its files never change. The main link opens the current version. A link to a specific version always opens the same files. An earlier version can be restored without deleting later history.

If someone else published first, the server refuses to replace the newer work and explains how to try again. Retrying the same request key returns the same version. Reusing that key with different input is rejected. Starting a new publish with a new request key creates a new version even when its manifest matches an earlier version. Restoring changes the current pointer; it does not create or alter a saved version.

Compare any two versions

Every saved version already lists each file's path, size, and SHA-256 fingerprint. Comparing those lists shows which files were added, removed, renamed, or changed. The server reads only changed text files to show changed lines. Images and other binary files open individually from each version.

For images, PDFs, audio, video, ZIP archives, and other binary files, the first release reports that the file changed and shows its old and new size and fingerprint. It does not build image-comparison, PDF-comparison, archive-preview, or media-conversion interfaces. Unchanged files reuse the stored copy with the same fingerprint. Without Git, the extra cost is small version metadata plus work performed only when someone requests a comparison.

Optional Git history

An administrator can enable a private Git copy when installing the server. Each artifact gets one repository, and each saved version maps to one commit. Git is not required for saved versions or comparisons.

Cloudflare deployments use Cloudflare Artifacts. Self-hosted deployments store Git repositories in the Artifact Server data folder, use a small internal Git storage service, or connect to an existing private Git server.

Plannotator integration

One Artifact Server installation can connect to one Plannotator organization. Plannotator owns sign-in, workspaces, workspace permissions, comments, and review state. Artifact Server owns artifact files, saved versions, browser delivery, and comparisons.

Example: a reviewer comments on a button in version 12. Plannotator saves the comment with the artifact ID, version 12's ID, and information that identifies the button. If version 13 is published later, opening the comment still loads version 12. Artifact Server returns the saved files and Plannotator returns the comment. Artifact Server never stores the comment.

Normal artifact links return the stored files unchanged. An explicit review address may add a small review bridge to the HTML response for that session only. The bridge receives no reusable credential, and the stored version remains unchanged.

Original files

People can download the exact files that were published. Opening or downloading an artifact does not alter the stored version.

Sharing

One person or team, with two access settings

One Artifact Server installation contains one closed group of people. This is a single-organization model without an organization list or organization switcher: the installation itself is the group. On a laptop, that can be one implicit local user. On a team server, an administrator controls who can sign in through invitations or the configured company login. The product has no public self-sign-up and does not host several organizations inside one installation.

S

1. Account required

This is the default. Only people admitted to this installation can open the item. In the standalone namespace, every admitted person can read every account-required item. A person outside that group cannot open it. Plannotator-managed artifacts live in a separate area controlled through the Plannotator connection and do not inherit this standalone read rule.

P

2. Public link

No account is required to open the item. Anyone who can connect to this Artifact Server and has the unpredictable link can open it. Public links are unlisted and send X-Robots-Tag: noindex, nofollow by default, but that is not an access-control guarantee. The public link opens only the current version. Version lists, comparisons, and earlier saved versions still require an account.

A public link removes sign-in. It does not put the server on the internet.

It does not open a firewall, create an internet tunnel, or change who can connect to the server. If Artifact Server runs inside a private company network, a public link still works only for people who can connect to that network. An administrator can disable public links.

Deployed processes expose one operational contract.

Every HTTP and MCP response receives a server-generated request ID. Artifact Server records request counts, handling time, and Effect spans. It samples normal request logs and always logs server failures and requests that take at least one second. Standard OpenTelemetry environment variables can send all three signals to an OTLP collector. Telemetry uses matched route patterns and never records authorization values, cookies, query strings, file contents, raw artifact IDs, or raw unbounded paths. /health reports whether the process is alive. /ready separately checks validated configuration, completed migrations, the database, and file storage; a dependency failure returns HTTP 503 without changing process health.

Plannotator connection

One approval connects the products

A reachable Artifact Server connects to one Plannotator organization from one approval screen. Plannotator controls who may use a workspace. Artifact Server still verifies every request and serves only the named artifact or version.

Connect

An Artifact Server administrator opens Plannotator, chooses one organization, and approves the connection.

Authorize

Plannotator checks the workspace permission and signs a short-lived request for one operation.

Open

Artifact Server creates a one-use URL and a temporary, read-only browser session for the exact version.

Review

An explicit review address adds the review bridge. Normal artifact responses and stored files stay unchanged.

One server, one Plannotator organization

The first Plannotator integration release does not add a multi-organization switcher to Artifact Server. The connection belongs to one Plannotator organization and can be disconnected or have its keys rotated by an administrator.

Separate storage areas

Standalone artifacts keep normal Artifact Server access. Plannotator-managed artifacts are bound to a workspace and cannot be browsed through a normal standalone session. Connecting the products does not silently migrate existing artifacts.

Private servers require a route

Hosted and publicly reachable servers connect from the approval screen. A server inside a private network also needs a customer-provided route or an outbound-only connector limited to Artifact Server. The connection does not change firewall rules or provide general access to the private network.

Bounded integration work

Connection, publishing, and opening are estimated at three to five engineer-weeks. The first supported review bridge adds three to six engineer-weeks. Private networking based on an established tunnel adds two to four engineer-weeks.

These estimates exclude Plannotator's existing organizations, Workspaces product, comment system, and the normal Artifact Server product. The teams must replace the estimates after inspecting both repositories and completing the browser and network prototypes.

The detailed handoff is ready for the Plannotator team.

It defines the connection record, signed request, browser session, review bridge, private-network choices, failure behavior, work split, investigation questions, and acceptance tests. Open the Plannotator and Artifact Server integration specification.

Architecture

One product core with deployment-specific storage

The browser, MCP, and normal web requests from software follow the same rules for sign-in, sharing, versions, comparisons, and publishing. Small pieces of code connect those rules to the database, file storage, and optional Git provider selected when the server is installed.

How a large website or file is published
  1. The client creates an upload and receives a unique staging location.
  2. It sends regular files directly to disk or cloud file storage.
  3. The server verifies every size and SHA-256 fingerprint and rejects unsafe or colliding paths.
  4. The client names the entry file, states the version it started from, and sends one idempotency key for the request.
  5. The server writes missing content-addressed blobs without overwriting an existing blob, saves the immutable manifest and version, and updates the current-version pointer in one database transaction.
  6. A retry with the same key returns the stored result. Scheduled work deletes only expired staging uploads in the first release.

Object storage and the database cannot commit atomically. The safe order is stage, verify, write each blob once, then commit the database records. The first release intentionally keeps committed or orphaned blobs. Reference garbage collection is added only after a lease-based or mark-and-sweep design survives crash, retry, and concurrent-publish tests.

How optional Git history works

Artifact Server always saves the version record, file list, fingerprints, and published files first. When Git history is enabled, it then copies that version into one private repository for the artifact. Each saved version maps to one commit, and the database records the Git commit identifier.

Git never supplies the files used to open the artifact. If the Git provider is unavailable, the saved version remains available and the server retries the Git copy. 

history:
  git:
    enabled: true
    provider: auto

Git history is off unless an administrator enables it. With provider: auto, the server chooses the provider that matches the deployment.

Deployment Git provider when enabled
Laptop or one server Git repositories stored inside the Artifact Server data folder.
Kubernetes A small internal Git history service with persistent storage, or an existing private Git server.
Cloudflare Cloudflare Artifacts.

Large files remain in the normal file store. Their names, sizes, and fingerprints stay in the Git version manifest. An administrator sets the largest file or artifact copied into Git. Cloudflare Artifacts currently limits each repository to 10 GB and does not document Git's separate large-file extension, called Git LFS. It is also in closed beta.

Git repositories remain private. A public artifact link never grants Git access or exposes earlier versions through a Git remote.

How isolated version addresses and private delivery work

Hosted deployments use an application address plus a unique content host for each saved version:

app.example.com
v12-7f3a.content.example.net

The content domain is separate from the application's registrable domain. Each saved version receives its own origin, so root-relative paths and service workers stay inside that version. Application cookies are host-only. The content service accepts only GET and HEAD, sends no credentialed CORS responses, and cannot change application data. The application also enforces CSRF tokens, trusted origins, and Fetch Metadata on browser mutations.

For account-required content, the application checks the viewer and creates a short-lived, single-use bootstrap token for one version host. That host exchanges the token for a Secure, HttpOnly, host-only content cookie. Relative CSS, JavaScript, image, and font requests then work without exposing an application credential. Private content is not placed in a shared CDN cache in the first release.

The current public version uses immutable cache keys and may be cached by a CDN. Publishing a new current version or changing the artifact to account required purges the previous public version from supported caches and stops new public origin requests. It cannot revoke copies already downloaded or retained outside the server. The interface must state that limitation before it is first made public and again before access is changed.

The stable application link checks access and selects the current version. The version link stays fixed. A static-site artifact returns 404 for a missing path. A single-page application may return its entry HTML only for browser navigation requests; a missing JavaScript, stylesheet, image, or other asset still returns 404. Responses use an explicit media type, nosniff, ETag, and safe download disposition. Media supports byte ranges.

How local file links fit

Local file import is available only through the local helper, when the helper and server can read the same disk. An administrator configures allowed root folders. The helper resolves the real path, rejects symlinks and special files, verifies that every file remains inside an allowed root, and copies the current bytes into staging. Changing the original file never changes a saved version.

A remote server never accepts a client filesystem path. The agent uploads the bytes. The first release does not fetch arbitrary source URLs, which avoids a server-side request path into private networks and cloud metadata services.

How deletion, retention, backup, and restore work

A committed version cannot be edited or deleted by itself. Deleting an artifact creates a tombstone and stops every application and content link. The first release does not immediately remove blobs, because reference reclamation must not race a publish, retry, backup, or restore.

A team deployment is not ready until backup and restore preserve installation, artifact, version, manifest, and action IDs and an integrity check confirms that every referenced blob exists. Retention duration, tombstone duration, physical deletion, recovery-point target, and recovery-time target remain deployment policy and release-gate decisions.

AI agent access

MCP sends publishing instructions and small results; large website and file uploads go directly to file storage.

Skills shipped with Artifact Server

Two skills with different permissions

Artifact Server ships two Agent Skills: small folders of instructions that Codex, Claude Code, and other compatible clients can install. Publishing and server operation stay separate. This keeps routine publishing instructions short and prevents an ordinary publishing request from loading deployment or administrator instructions.

publish-artifact

The normal skill. It is used when someone asks an agent to publish, update, open, share, list, or compare an artifact. It connects through MCP and uses the signed-in person's normal Artifact Server permissions.

  • Resolve which local or team server the user means before reading, publishing, or opening an artifact.
  • Ask the server what it supports before choosing an upload method.
  • Publish one actual file or one finished directory. Do not place raw source text or base64 file contents in MCP arguments.
  • Choose the supported upload method without asking the user to construct a manifest, fingerprint, or upload session.
  • Return the artifact link and exact saved version after publishing.
  • Never install, upgrade, reconfigure, back up, or delete an Artifact Server installation.

operate-artifact-server

An optional administrator skill. It is used only when someone explicitly asks an agent to install, deploy, upgrade, back up, restore, inspect, or repair Artifact Server. It uses the Artifact Server command-line program and the selected deployment adapter.

  • Read only the instructions for the selected target: laptop, server, Kubernetes, Cloudflare, AWS, GCP, or Azure.
  • Show the proposed change before applying it and verify health after it finishes.
  • Require administrator access. It does not gain infrastructure access through the publishing MCP connection.
  • Remain an explicit, separately installed skill because its actions can change running infrastructure.
How an agent chooses the local or team server

Every artifact reference includes the Artifact Server address, artifact ID, and, when needed, the exact version ID. An artifact ID by itself is not enough because the same person may use a local server and one or more team servers.

The publishing skill resolves the target in this order:

  1. An Artifact Server address, artifact link, or named server stated in the current request.
  2. The server contained in an artifact reference already present in the conversation.
  3. The server used by the artifact most recently published or opened in the current conversation.
  4. The current project's configured default server.
  5. The user's default server.

If those rules do not produce one server, the agent asks whether to use the local or team server. It never publishes to, reads from, or opens an artifact from a guessed server.

The Artifact Server command-line program keeps named connection profiles such as local and team. A project may contain an optional, non-secret .artifactserver.json file that names its default server address or connection profile. User defaults, recent artifact references, and the local server's current address remain in user-local state. Access credentials stay in the MCP client or operating-system credential store; they are never written into the project file.

The MCP artifact_open tool returns the canonical browser address for the chosen artifact and version. A local helper may ask the operating system to open that address directly. A remote server only returns its address; the agent or client opens it on the user's computer. The remote server never attempts to start a browser on the server machine.

Skill packaging, installation, and updates

Both skills use the open Agent Skills folder format and ship in the official Artifact Server repository under skills/publish-artifact and skills/operate-artifact-server. They are listed on skills.sh and can be installed into Codex, Claude Code, and other compatible clients with the npx skills installer. The final copy-and-paste command is published after the official repository address is fixed.

The skill name is the portable contract. A client may display it as a slash command, but Artifact Server does not depend on slash-command spelling because that behavior differs between clients. Each skill contains a short main instruction file. Detailed upload errors and deployment-specific procedures live in separate reference files that the agent reads only when required.

The publishing skill does not contain a cloud-specific configuration. It calls artifact_capabilities at the start of a publishing task. That response reports whether the server is local or remote, the file-count and upload-request limits, the exact upload workflow, supported sharing settings, and the text-comparison bound. The same installed skill therefore works with a laptop, private server, Kubernetes, or hosted service.

Skills are versioned with Artifact Server releases and tested for correct activation as well as correct output. A skill tells the user when the connected server is too old for a requested operation. The release process tests realistic requests that should activate each skill and similar requests that must not.

Format and distribution follow the current Agent Skills specification and the skills.sh directory and installer.

The modern MCP server contract

The primary endpoint uses MCP revision 2026-07-28 and the official TypeScript SDK version 2. Every request is independent. There is no initialization handshake, MCP session identifier, sticky load-balancer route, or permanent event stream. The client calls server/discover to learn supported protocol versions and server instructions, then uses tools/list and resources/templates/list for the current catalog. It calls artifact_capabilities for deployment-specific limits and publishing behavior.

  • Remote external-storage installations use HTTP POST /mcp.
  • Normal results use JSON. Request-scoped server-sent events are reserved for useful progress.
  • The first release rejects subscriptions/listen. It is enabled only after the deployment has a real shared event service.
  • Modern GET /mcp and DELETE /mcp return 405. Older MCP behavior is an isolated, optional compatibility path.
  • Every durable change has an application idempotency key. A change to an existing artifact also includes the version the caller started from. A broken connection cannot silently publish twice or overwrite newer work.
Hosted OAuth and Artifact Server's responsibility

In the hosted service, WorkOS owns the authorization page, approval screen, authorization codes, client registration, access credentials, renewal, and revoke behavior. Artifact Server remains the protected service. It publishes the standard metadata that tells clients where to sign in and verifies every credential before an MCP request reaches product code.

The credential must name the exact Artifact Server MCP address as its audience and include the mcp scope. Artifact Server also verifies the issuer, signature, expiry, and user, then maps that user to an account admitted to this installation. Artifact Server does not copy WorkOS organizations into a second organization system. The same artifact ownership and write checks used by the browser still apply.

The hosted authorization service enables Client ID Metadata Documents first and keeps Dynamic Client Registration temporarily for clients that still require it. Authorization uses the browser authorization-code flow with S256 PKCE. WorkOS credentials never pass to file storage, background workers, or published websites.

The exact wire behavior, metadata, token checks, self-hosted modes, and release test matrix are recorded in the Artifact Server MCP engineering baseline.

How agents connect and avoid overwriting newer work

Remote agents use HTTP POST /mcp. On the same computer, a small command-line helper or loopback listener uses a local token and calls the same product service. The helper never writes directly to the database.

Every change includes the version the agent believes is current. If newer work exists, the server returns the actual current version and tells the agent what to read before trying again. Retrying the same idempotency key returns the same result. Starting a new publish with a new key creates a new version even when the bytes match an earlier version. Creating a brand-new artifact has no earlier version. Creating an uncommitted upload is temporary preparation and does not alter an artifact.

Compatibility and release checks

The released July 2026 protocol is the product target. Compatibility with older MCP clients is not mixed into the modern path. If a required client still uses the older initialization handshake, an administrator can enable a separately tested compatibility handler.

Release testing covers current Codex, Claude Code, Claude.ai, and at least one DCR-only client. Each is tested with a fresh connection, an old cached connection, an expired credential, a revoked grant, a wrong audience, an invalid origin, and a user who has not been admitted to that installation. Claude.ai can reach only Artifact Servers exposed to Anthropic's cloud; a server reachable only inside a private network is not supported there.

Deployment

Supported deployment targets

A local installation starts as one process running directly on the host with one data folder and does not require Docker. A team deployment may run several copies of the application, all using the same database and file storage. The product defines runtime and storage interfaces; official infrastructure packages select the provider-specific services.

Local first

One process runs directly on the host with one SQLite database file and local disk. Docker is optional. Local browser addresses use *.localhost, so no DNS or certificate setup is required.

Private team

Compact Compose runs one container with SQLite and attached disk. External-storage Compose uses the same image with existing Postgres and object storage, and it can run multiple application processes.

Cloudflare

Cloudflare Workers, D1 records, R2 files, nearby copies of public files, and optional Cloudflare Artifacts history.

Major clouds

AWS, GCP, and Azure use the same container or Kubernetes runtime with Postgres and the provider's native object store.

Each standalone deployment is one installation for one person or team. The hosted artifactserver.com service may run many isolated installations on shared Cloudflare infrastructure. The installation identity comes from trusted authentication and routing, never from a caller-supplied filter. Tenant-scoped storage APIs, composite keys, cache keys, signed links, background jobs, backups, and restore tests enforce the boundary.

How it is installed and how people sign in

The product ships as a downloadable local package that does not require Docker, one optional container image, Compact Compose and External-storage Compose for one server, a Helm chart for Kubernetes, an Alchemy-backed Cloudflare package, and Pulumi-backed packages for AWS, GCP, and Azure. Each package pins its tool version and emits a deployment manifest for support. These are install paths for one product, not separate editions.

Browser login and MCP authorization are separate protocols even when they use the same identity provider. Team browser login may use OpenID Connect. Hosted MCP connections use WorkOS AuthKit. Private installations can use server API keys or a compatible authorization service. A single-user installation may rely on the operating-system account or a local token.

How the same code works with different databases and file storage

The product rules do not know which database or file storage is in use. Each deployment supplies small pieces of code for saving records, saving files, signing users in, and running cleanup work. The product rules do not call Node.js file functions or a specific database library directly. Optional Git history follows the same rule through one small provider interface.

  • Laptop: one process runs directly on the host by default, with SQLite for records, files stored on disk by their SHA-256 fingerprints, optional local file links, and optional Git repositories in the same data folder. Docker is optional.
  • One server, compact: one process, SQLite in write-ahead logging mode, one persistent data directory, and optional Git repositories in that directory. This profile does not support multiple application writers or claim failover.
  • One server, external storage: the same image connected to existing Postgres and object storage through a supported adapter. The Compose package does not bundle those providers.
  • Kubernetes: Postgres plus S3, Google Cloud Storage, Azure Blob, R2, or compatible object storage, with an optional internal Git history service or private Git server.
  • Cloudflare: Workers for the application, D1 for records, R2 for files, and optional Cloudflare Artifacts history. External Postgres is supported through a separate adapter but is not the default.
  • AWS, GCP, and Azure: the same container or Kubernetes runtime, managed Postgres, and the provider's native object store. Pulumi supplies the official infrastructure package.

The storage boundary uses product operations such as “publish this version only if the current version has not changed,” not a generic function that sends raw SQL to any database. SQLite/D1 and Postgres keep their own migrations, indexes, transactions, and optimized queries. External-storage tests prove that publishing, access, versions, and cleanup behave the same.

The first external-storage package supports AWS S3 and Cloudflare R2 through its S3 adapter. Another S3-compatible service is supported only after it passes the same storage contract tests. Native Google Cloud Storage and Azure Blob adapters ship with their cloud packages. Adding an adapter does not change artifact or version rules.

When Caddy, DNS, and certificates are needed

Local use on the same computer needs none of them. Artifact Server binds to loopback and uses *.localhost. The same rule applies to an optional local container reached only from that computer.

A one-server installation opened from other devices needs HTTPS routing for the application address and the wildcard content address. Caddy is the documented example only when the team has no existing reverse proxy. Nginx, Traefik, HAProxy, or a company gateway can be used when it passes the same routing, upload, and TLS tests. Kubernetes uses its Ingress or Gateway. Cloudflare and managed-cloud packages use their provider edge. Those deployments do not run Caddy.

Why D1 is the Cloudflare launch default and what must be proven before it grows

D1 stores small relational records: installations, accounts, artifacts, saved versions, file paths, fingerprints, access settings, credentials, and cleanup state. R2 stores the artifact files. An artifact file never goes into D1.

The hosted service starts with one production D1 database. The authenticated installation identity is bound before product code reaches storage. Composite database keys, R2 prefixes, cache keys, signed links, jobs, backups, and restore paths all include that trusted identity through a tenant-scoped storage API. Remembering to add an installation_id filter is not an adequate boundary.

Hosted storage growth Start with one D1 database. Choose and test a control plane before adding another.
Used at launch Added after measured need

The proposal does not claim that adding D1 databases is automatic. Before a second database, the team must choose and load-test either a D1 directory plus safe binding rollout or an external Postgres control plane. That decision must cover provisioning, tenant moves, retries, backups, restore, and rollback.

D1 has a hard 10 GB limit per paid database and processes writes through one primary database. Global read replicas can reduce read latency when the Sessions API is used, but they do not scale writes. Artifact metadata remains much smaller than the files in R2. Measurements decide whether D1 sharding or external Postgres is the safer growth path.

D1 scales to zero and includes substantial monthly reads and writes on Workers Paid. R2 stores Standard files for $0.015 per GB-month beyond the included allowance and does not charge for internet data transfer. External Postgres would add another provider, region, connection pool, credentials, backups, and another network failure path.

Publishing across D1 and R2 follows this order:

  1. Upload each file to a unique staging key.
  2. Verify size and fingerprint, then create the final blob without overwriting an existing object.
  3. Commit the manifest and version in D1 only if the current version is still the expected version.
  4. Return the recorded result when the same idempotency key is retried.
  5. Delete only expired staging uploads in the first release. Keep committed and orphaned blobs until a concurrency-safe garbage collector exists.

Current platform references: D1 limits, D1 pricing, D1 global read replication, and R2 pricing.

Safety and trust

Treat every published website as untrusted code.

A published website may run arbitrary browser JavaScript. The architecture isolates each saved version and keeps application credentials out of the content origin.

Unique origin for every version

The application and content use separate registrable domains. Every saved version gets a unique content host. Application cookies are host-only; content is read-only; credentialed CORS is disabled; browser changes require a CSRF token, trusted Origin, and valid Fetch Metadata.

Private content session

Account-required content begins at the application. After permission is checked, a single-use token creates a Secure, HttpOnly, host-only session for one exact version host. Relative assets use that session. It grants no write operation and no access to another version.

Public links cannot recall copies

Changing a public artifact back to account required purges supported caches and stops new public requests. It cannot revoke files already downloaded or cached outside the service. The product states this before the change.

Safe upload inputs

Portable manifest rules reject path traversal, absolute paths, symlinks, special files, duplicate normalized names, and case or Unicode collisions. A local publishing client reads only files allowed by its operating-system identity and uploads their bytes immediately. HTTP and MCP never accept a client filesystem path or fetch an arbitrary URL.

Tenant-scoped storage

The installation identity comes from trusted authentication and routing. Product code cannot issue an unscoped database, object-store, cache, background-job, backup, or restore operation. Cross-tenant tests cover every one of those paths.

Private Git history

Optional Git repositories remain private. Making an artifact available through a public link never grants Git access or exposes its earlier versions through a Git remote.

Recorded responsibility

Publishing actions record the signed-in user, agent, or automated account that performed the action.

Server policy

Administrators control login, whether public links are allowed, file limits, retention, network rules, and accepted file types. Hosted service policy also covers abuse reports, phishing and malware response, quotas, egress limits, and content-domain reputation.

Scope

Product scope

The product supports the shortest path from finished output to a stable browser link. The implementation section phases delivery; this section defines the final product boundary.

Included

  • Finished client-side output directories and arbitrary individual files.
  • Saved versions that never change, plus the ability to restore an earlier one.
  • File and text comparisons between any two saved versions.
  • Optional private Git history selected when the server is installed.
  • Exactly two access settings: account required and public link.
  • Browser access, MCP, and normal web requests from software.
  • An optional connection from one Artifact Server installation to one Plannotator organization, including signed operation requests and temporary browser sessions.
  • An explicit Plannotator review response that may add a credential-free review bridge without changing the stored artifact.
  • A portable publish-artifact skill and a separately installed operate-artifact-server administrator skill.
  • Local, one-server, Kubernetes, Cloudflare, AWS, GCP, and Azure deployment packages delivered in stages.

Not included

  • Comments, annotations, replies, review status, notifications, or workspace collaboration. Plannotator provides these features.
  • A general-purpose Git service for arbitrary source-code repositories. Optional Git history exists only for Artifact Server artifacts.
  • Installing packages or turning source code into a finished application.
  • Code inside an artifact that must run on the server.
  • Media conversion, thumbnails, ZIP extraction, Markdown rendering, source-code highlighting, custom PDF viewing, or specialized binary comparisons in the first release.
  • Fetching arbitrary source URLs from the server.
  • Add-ons that run inside Artifact Server.
  • A separate Artifact Server-managed user list for every standalone artifact. Plannotator may apply its workspace rules before sending a managed request.
  • Automatic firewall changes or a general-purpose tunnel into a customer's network. An optional connector may expose only the paired Artifact Server service.
Implementation

Implementation order

Each stage keeps the same product behavior. Code that connects a deployment to its database and file storage must not copy or change the product rules.

The specification has an executable checklist.

Every product promise, security rule, exclusion, deployment claim, and unresolved release gate has a stable ID, an owning module, a normal test, a hostile or failure test, applicable deployments, status, dependencies, and evidence in conformance.yml. A requirement is complete only when both tests pass on every applicable deployment and the proof is recorded there. Read the validation and release-gate instructions.

First

One complete local product

Build saved versions that never change, comparisons between versions, support for complete client-side output directories, the separate artifact website, SQLite and local file storage, the modern stateless MCP route, web publishing, local-token access, the two sharing modes, and optional Git repositories in the local data folder. Ship the publish-artifact skill after its MCP workflow is stable. Reject MCP subscriptions until a real event service exists. Ship it as one running application.

Next

The external-storage server

Keep SQLite for a single-server installation. Add Postgres and cloud file storage for Kubernetes or any deployment with multiple application replicas. Support S3, Google Cloud Storage, Azure Blob, R2, and compatible object stores through one narrow interface. Add browser login, API-key and external-issuer modes for private deployments, staged direct uploads, expired-staging cleanup, a Docker image, a Compose file, a Helm chart, backup and restore, and optional private Git history. Add structured request logs, standard OTLP export for logs, metrics, and traces, and separate process-health and dependency-readiness checks. Ship the optional operate-artifact-server skill after install, upgrade, backup, restore, and health-check commands are stable and tested.

Then

The Plannotator connection

Add browser approval for one Plannotator organization, signed requests limited to one workspace and operation, a single-use private artifact address, disconnect and key rotation, and connection audit records. Ship top-level private opening first. Add review mode only after the bridge passes hostile-artifact and browser tests. Use customer-provided networking or an established tunnel before building a product-owned connector.

Then

The Cloudflare deployment

Add Cloudflare Workers, D1 records, R2 file storage, and the optional Cloudflare Artifacts provider. Enforce tenant-scoped storage from trusted routing. Start the hosted service with one D1 database. Before a second database, select and test a D1 directory and binding rollout or external Postgres control plane. Copy to Git only after the normal saved version is complete, and retry temporary failures. Verify file delivery with and without an account, upload limits, complete website behavior, comparisons, and signed-in MCP access over the web.

After

Official AWS, GCP, and Azure packages

Ship pinned Pulumi packages for each cloud. Reuse the container or Kubernetes runtime, managed Postgres, and the provider's native object store. Test install, upgrade, rollback, backup, restore, private networking, and removal independently for each provider. Do not claim a provider is supported until those tests pass.

How we know each release is ready
  • Local: one process publishes one file and a complete static site, opens the unique version host, compares versions without Git, retries safely, and survives a restart.
  • Private team: account-required subresources load, forbidden mutations fail, backup and restore preserve IDs, and cross-tenant and hostile-path tests pass on one server and Kubernetes.
  • Cloudflare: WorkOS MCP sign-in, R2 staged uploads, D1 transactions, public cache purge, private no-cache delivery, abuse controls, and a restore drill pass under measured cost and load.
  • Plannotator connection: one-click approval, cross-organization rejection, signed-request scope, one-use browser links, disconnect, key rotation, exact-version comments, hostile review-page tests, and private-route failure and recovery all pass.
  • Major clouds: every provider package passes install, upgrade, rollback, backup, restore, private-network, and removal tests before support is advertised.
  • All releases: browsers open native file types without a conversion service; arbitrary URL fetch is absent; optional Git failure never blocks or loses the primary saved version.
Decision record

Decisions made by this proposal

These choices make the proposal internally consistent. The remaining unknowns are explicit release gates, not implied promises.

The product stores and serves finished client-side sites and arbitrary files. The browser handles supported formats natively. The server does not run artifact backends or perform file conversion.

An artifact keeps one identity. Each intentional publish creates an immutable version with a canonical manifest and unique version origin. Restoring only changes which version is current.

A retry with the same idempotency key returns the stored result. A new key creates a new version even when the manifest matches an earlier version.

An artifact may have up to 20 normalized tags for exact filtering. Tags belong to the artifact, persist across version changes and tombstones, and are replaced through one authorized, idempotent, audited operation. The first release has no tag hierarchy or per-version tags.

Comparisons use canonical manifests and changed text. Binary comparison shows metadata and links. Git is not required.

Git history is an optional private copy. The normal object store remains authoritative, and Git failure never blocks or loses a saved version.

Account required and public link are the only two read settings. A public link opens only the current version; history and comparisons still require an account. Publishing, access changes, and deletion follow a separate owner, administrator, and scoped-service authorization matrix.

A standalone installation is one person or one team. One installation may connect to one Plannotator organization. Plannotator-managed artifacts use a separate logical area that normal standalone sessions cannot read.

Plannotator checks workspace access and sends a short-lived, audience-restricted request. Artifact Server verifies it and creates its own one-use browser address and read-only content session. User accounts and browser login cookies are not copied.

An explicit review address may add a credential-free review bridge to HTML responses for that session. Normal responses and stored versions remain unchanged. Plannotator stores every comment and review record.

A private connected server uses a customer-provided route or an outbound-only connector limited to Artifact Server. Connecting never changes firewall rules or exposes the rest of the private network.

Every saved version uses a unique host on a content domain separate from the application domain. Private subresources use a version-scoped content session; public content may use immutable CDN caching.

Changing public content back to account required stops future public access and purges supported caches, but cannot recall downloaded or externally cached copies.

Manifest paths follow one portable safety contract. Publishing clients upload bytes. A local client may read a user-selected path with its operating-system permissions, but HTTP and MCP never receive that path. The server does not fetch arbitrary source URLs.

Uploads stage, verify, then write content-addressed blobs without overwrite before the database commit. The first release deletes expired staging only and does not garbage-collect committed blobs.

Browser, normal software requests, and MCP share the same product and authorization rules. Hosted MCP uses WorkOS AuthKit; local and self-hosted modes retain scoped API keys.

Artifact Server ships a routine publishing skill and a separately installed operator skill. Stored references include the server and artifact, so agents open local or team artifacts at the correct origin.

The product core uses narrow database, blob, login, background-work, and optional Git interfaces. Official deployment packages are Compose, Helm, Alchemy for Cloudflare, and Pulumi for AWS, GCP, and Azure.

Support is phased: local, private team and Kubernetes, hosted Cloudflare, then AWS, GCP, and Azure. A target is not supported until its install, upgrade, rollback, backup, restore, and isolation tests pass.

Committed versions cannot be edited or deleted individually. Deleting an artifact creates a tombstone and stops access; physical reclamation waits for a proven retention and garbage-collection design.

Known unknowns and required failure probes

  1. Private site delivery: prototype the bootstrap token and version-scoped cookie in major browsers, including relative assets, reloads, redirects, range requests, and expiration.
  2. Version origins: prove wildcard DNS, certificates, local *.localhost, service workers, root-relative paths, SPA fallback, and host-count limits.
  3. Cloudflare Artifacts: confirm closed-beta availability, repository limits, retry behavior, retention, regional behavior, and production support. The product must work when it is disabled.
  4. WorkOS MCP: complete staging probes for token lifetime, refresh rotation, revoke behavior, live claims, consent wording, DCR, CIMD, and stale client state.
  5. Embedded self-hosted OAuth: decide whether Better Auth's beta MCP path is mature enough; API keys and compatible external issuers remain the default until it passes the same hostile tests.
  6. Cross-cloud packages: prove pinned Alchemy and Pulumi versions, state storage, preview, rollback, provider drift, upgrades, and clean removal in CI.
  7. Hosted abuse: design quotas, egress limits, rate limits, phishing and malware response, reporting, suspension, and content-domain reputation protection before public hosting.
  8. Capacity and cost: load-test manifests, large directories, concurrent uploads, text diffs, CDN behavior, database write limits, and worst-case egress. Set hard limits from measured results.
  9. Recovery: define retention, tombstone duration, backup schedule, restore procedure, recovery-point and recovery-time promises, and an operator-visible integrity check.
  10. Enterprise data controls: decide encryption-key ownership, regional placement, audit export, legal hold, deletion proof, data residency, and regulated-content boundaries.
  11. Custom domains: decide whether customer domains are supported and, if so, how certificates, version isolation, cookies, cache purge, domain takeover, and service workers remain safe.
  12. Plannotator review bridge: test the isolated review response against hostile artifact JavaScript, strict content policies, multi-page sites, single-page routes, service workers, anchor stability, session expiry, and browsers without third-party cookies. Use a browser extension if the bridge cannot pass without exposing a reusable credential.
  13. Existing artifact attachment: decide whether attaching a standalone artifact to a Plannotator workspace moves it or copies it, and prove permissions, IDs, links, rollback, and disconnect behavior.
  14. Private Plannotator route: choose the first supported path among customer-provided networking, Cloudflare Tunnel, or a product-owned connector. Define health, upgrades, replicas, egress addresses, and failure behavior before advertising one-click private connection.
