# CI redesign — 2026-08-27

## Decision

Adopt a tiered workflow with a parallel PR tier and a complete full tier on
`main`, nightly schedule, manual dispatch, and `merge_group` if a merge queue is
enabled later.

The PR tier has one concern per job:

1. build and static policy;
2. root unit/conformance behavior using the shared build artifact;
3. browser behavior using the shared build artifact;
4. Cloudflare runtime/deployment behavior using the shared build artifact; and
5. the existing macOS portability gate.

The full Linux tier keeps the exact ordered direct-command expansion of
`pnpm verify:iteration`. A drift checker compares that workflow list to
`package.json`. The local `pnpm verify:iteration` command is unchanged.

This is candidate A below.

## Candidate A — tiered PR concerns, serial full gate (selected)

### Shape

- `pull_request`: build/static, root tests, browser, Cloudflare, and macOS run
  in parallel after one shared Linux build artifact where applicable.
- `push` to `main`: complete Linux gate plus macOS.
- nightly `schedule`: complete Linux gate plus macOS and durable evidence
  artifacts.
- `workflow_dispatch`: selects either the PR tier for repeatable branch trials
  or the complete Linux tier for qualification before merge.
- `merge_group`: complete Linux gate plus macOS, ready for a future queue.

### Why it fits the measurements

The predicted PR critical path is root test setup plus `pnpm test`: roughly
7–9 minutes from the four samples. Build/static is under three minutes,
Cloudflare under four, browser under five including setup, and macOS about five.
The design therefore has margin under the 12-minute target without paid
hardware.

The full tier retains the current serial behavior and its accidental reuse of
warm BuildKit layers. It changes observability—each direct command becomes a
named GitHub step—but not the ordered command set.

### Cost and risk

PR runner-minutes should fall because Docker, coverage, packaging, Helm, OIDC,
and performance leave PRs. Setup is duplicated across Linux concerns, but the
expensive pnpm cache restore is still much smaller than the work removed.

Main still spends roughly the current 36–48 rounded runner-minutes and gains an
evidence upload. A bad merge can make `main` red for the duration of the full
gate, but the full run begins immediately. This is acceptable for a pre-release,
low-PR-volume repository under the brief's “before or immediately upon landing”
constraint. It is not acceptable once `main` is a release branch with external
consumers; that is the point to enable candidate C.

## Candidate B — fully fanned full gate with shared OCI/build artifacts

### Shape

Use candidate A's PR tier, then split the full tier into storage, coverage,
performance, local package, compact Compose, external Compose, Helm, and OIDC
jobs. Build the compiled tree and one attested OCI archive once, upload both,
and teach integration scripts to consume a verified prebuilt archive in CI.

### Benefits

- Full-tier wall-clock could approach 10–15 minutes instead of 30–43 minutes.
- Compose and Helm concerns become independently retryable and easier to
  diagnose.
- One OCI byte sequence is tested across all release packages.

### Why it is not selected now

- It changes integration-script execution semantics before the basic tiering
  is proved. The scripts currently build their own image as part of each local
  boundary.
- The multi-platform OCI archive and attestations are large. Upload/download
  latency, artifact quota, revision verification, and partial upload failure
  become new release-gate dependencies.
- Cold Docker setup and pnpm restores multiply across many jobs. Billable
  minutes may rise even if wall-clock falls.
- Independent evidence writers need an explicit collision-free merge policy.

This remains a second iteration if the measured full gate itself becomes an
operations bottleneck.

## Candidate C — merge queue with the full gate before `main`

### Shape

Use candidate A's fast PR checks for normal feedback, require the complete tier
on `merge_group`, create a `main` ruleset requiring pull requests and merge
queue, and prevent direct pushes except an explicit break-glass bypass.

### Benefits

- Every merged commit has already passed the complete gate at the exact queued
  merge SHA.
- `main` does not spend 30–43 minutes in an unknown state after merge.
- Queue serialization prevents independently green PRs from breaking in
  combination.

### Why it is not selected now

- The repository has only ten historical PRs and most of the last 30 CI runs
  were direct pushes to `main`. A merge queue would not protect that current
  path unless the ruleset also prohibited direct pushes, a larger workflow and
  owner-behavior change than CI tiering.
- The complete gate currently takes up to about 43 runner minutes. Requiring it
  for each queue candidate would restore the long merge wait the assignment is
  meant to remove, only later in the interaction.
- There is no existing branch protection or ruleset to migrate. Introducing a
  queue, required PRs, bypass policy, and new checks simultaneously has a
  lockout and starvation risk.

The workflow keeps `merge_group` support so this candidate can be enabled after
full-tier fan-out or a larger-runner decision reduces its critical path.

## Detailed choices

### PR checks

The build/static job runs lint, typecheck, production build, site verification,
both conformance ledger checks, both Pulumi verification suites, and the CI/full
gate drift checker. It uploads only compiled application/web outputs.

The root-test job downloads those exact outputs and runs `pnpm test`. This is
the longest predicted PR job and produces the local-foundation evidence report.

The browser job downloads the same outputs, installs Chromium, runs the full
Playwright suite, writes browser evidence, and uploads traces/reports on
failure. It does not call the normal `test:web` script because that script
intentionally rebuilds for local use; an additive prebuilt CI command preserves
the local behavior.

The Cloudflare job downloads the same web output and runs lint, typecheck, and
Vitest directly. It deliberately bypasses the package `pretest` web rebuild in
CI while keeping `check:cloudflare` unchanged locally.

The macOS job remains `pnpm check`. It is already off the critical path and
exercises actual Darwin filesystem and CLI branches. Narrowing it is deferred
until a dedicated portability suite exists.

### Browser sharding and retries

Do not shard initially. The complete browser command measured 2m16s–2m51s;
setup and Chromium installation are comparable to the test time. Two or three
shards would add pnpm cache downloads, browser installs, evidence merging, and
shard imbalance around the large `frontend-mvp.spec.ts` without shortening the
predicted PR critical path.

Do not add retries. The known navigation/layout races are fixed in `811a817` and
the branch starts after that commit. A retry can hide a recurrence. If trials
find a new browser-only flake, fix the observable wait using `expect.poll` or a
navigation wait, record it, and only then consider one bounded Playwright retry.
Unit and conformance checks are never retried.

### Path filters

Do not add path filters in the first iteration:

- AWS and GCP checks together cost under 20 seconds and import the shared
  deployment contract from `src/**`.
- Cloudflare bundles application/web behavior; a deploy-only filter would be
  incorrect.
- Helm and Compose are absent from PRs entirely, so filtering them cannot
  improve PR wall-clock.
- A stable set of required checks is simpler than conditional required jobs and
  makes ruleset configuration less error-prone.

A future site-only optimization can be driven by changed-path metadata after
the stable PR tier is measured.

### Caches and artifacts

Keep the current pnpm store cache for the trial so before/after attribution is
clear. Cache Playwright browsers only if the first trial shows download time is
material; the current maximum is 49 seconds and is not on the predicted
critical path.

Use a short-retention build artifact for `dist/**`, including `dist/web/**`. The
artifact contains no credentials and comes only from the same workflow run.
Downstream jobs verify they received both trees before executing.

The full tier uploads generated evidence and diagnostics after success. Failed
browser runs upload Playwright output/traces separately. Action versions remain
pinned to immutable SHAs and permissions remain `contents: read`.

### Required checks and repository settings

After the PR is green, require the stable PR-tier job names plus the existing
Security Scanning jobs. Do not create a merge queue or require the full gate on
ordinary PRs. The full tier is required by workflow behavior for `merge_group`
if a queue is enabled later.

The ruleset change must happen only after three consecutive green PR-tier runs,
and its exact API request and reversal must be recorded in the final report and
PR body.

## Evaluation after trials

Three consecutive PR-tier runs and the full-tier qualification run are recorded
in the performance profile and final report. The first trial before the streak
found an artifact extraction-path mistake; the build job was green, but the
three consumers correctly failed their explicit `dist` checks. The path was
fixed, the artifact actions were updated to their current Node 24 releases,
and the branch was not changed during the three qualifying runs.

### Did PR wall-clock reach 12 minutes?

Yes. Runs
[33090070630](https://github.com/plannotator/artifact-server/actions/runs/33090070630),
[33090950570](https://github.com/plannotator/artifact-server/actions/runs/33090950570),
and
[33091836813](https://github.com/plannotator/artifact-server/actions/runs/33091836813)
were green in 9m 21s, 9m 41s, and 9m 16s. The median is 9m 21s, leaving
2m 39s of margin. Root unit/conformance behavior after the shared build is the
stable critical path; browser, Cloudflare, build/static, and macOS all finish
earlier.

### What runs later, and what can a bad merge do?

By design, object-storage emulators, external-storage
runtime, coverage diagnostics, local package, performance, Compose, Helm, and
OIDC move from pre-merge PR execution to the immediate `main` full run. The PR
tier still covers the broad root suite, browser UI, Cloudflare runtime, builds,
types, lint, conformance indexing, and Pulumi graphs.

A defect isolated to a remote-storage adapter, packaged image, Compose/Helm
recovery, Keycloak integration, or a measured performance bound can therefore
reach `main` and leave its full gate red until corrected. It cannot silently
produce a green full gate: the exact command list is preserved and evidence is
uploaded. For this pre-release repository, with no automated release following
the CI job, immediate post-merge detection is acceptable. It stops being
acceptable if `main` becomes continuously releasable; enable candidate C after
reducing the full-tier critical path in that case.

### Billable-minute change

The three PR trials consumed 24, 24, and 23 rounded job-minutes, averaging
23.7. The four baseline samples averaged 44.0, so an ordinary PR run uses 46.2%
fewer raw billable job-minutes even though setup is duplicated. The full
`main` run remains approximately baseline cost. For a PR that merges, the old
shape paid for the full gate on both the PR and `main`; the new shape pays about
24 minutes plus one full gate, saving roughly 20 minutes per merged PR.

The new daily schedule adds one full gate per day even when there is no change.
At the observed baseline average that is about 44 rounded job-minutes/day, so
it breaks even against PR savings at roughly two PR runs per day. The schedule
buys dependency, runner-image, and emulator drift detection; if the repository
stays dormant, reducing it to weekdays is a defensible cost follow-up. Actual
charged dollars could not be queried because the token lacks `admin:org`.

### New failure modes

The shared build artifact adds service/upload/download failure and path-layout
risk. The first trial caught the latter. Every consumer now checks the expected
compiled CLI and web entry points before testing, and the artifact is scoped to
one run with short retention. Fan-out downloads the approximately 514 MiB pnpm
cache four times, increasing cache bandwidth even as job-minutes fall. There is
no cross-run build cache or untrusted cache writer, so cache poisoning exposure
did not expand. The design has no shards, evidence merge, or retry ambiguity.
The remaining operational risk is a narrower green PR followed by a red full
`main` gate, accepted above.

### Rejected work

The current decision rejects paid larger runners, browser sharding, automatic
retries, path filters, OCI artifact fan-out, and a merge queue for the reasons
above. Revisit only if measurements invalidate the predicted critical path.
