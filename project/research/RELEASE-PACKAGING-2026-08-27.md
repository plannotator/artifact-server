# Artifact Server release packaging inventory

Date: 2026-08-27  
Source revision: `c69eaaf0a357fb931afad158aa7b7ece9cd9e655`  
Target release: `v0.1.0` pre-release

## Conclusion

Artifact Server already has credible local-package and OCI builders. They build
the real application, remove development-only files, validate runtime metadata,
and exercise meaningful replacement and persistence behavior. The release pass
should extend these builders with registry publication, checksums, public
attestations, and clean-install verification. It should not create another
packaging path.

The three agent adapters are separate MIT-licensed npm surfaces. The proposed
`@artifact-server` npm organization does not exist. The authenticated publisher
has write access to `@plannotator`, and these names are unclaimed:

- `@plannotator/artifact-server-pi`
- `@plannotator/artifact-server-opencode`
- `@plannotator/artifact-server-claude-channel`

The root package stays `private: true`. The server is distributed as the
portable tarball and OCI image, not as an npm package.

The npm publisher is `backnotprop`. The `@artifact-server` organization is not
registered, while the publisher has access to `@plannotator`. Registry checks
on 2026-08-27 confirmed the three selected `@plannotator/artifact-server-*`
names were unclaimed.

- `scripts/build-oci-image.sh`: default image name is the placeholder
  `artifactserver.com/artifact-server`.
- Shipping adapter READMEs and the public agent documentation use the old npm
  names.

### Generated evidence that must be refreshed

- `project/evidence/local-package-build.json` records the last built archive as
  `artifact-server-0.0.0-node.tar.gz`.
- `project/evidence/local-capacity-baseline.json` records product version
  `0.0.0`.

These files are outputs of the existing verification commands. They should be
regenerated by the release gate, not hand-edited to look current.

### Intentional internal values

- Private workspace packages under `apps/` and `deploy/` are not published
  release surfaces. Their `0.0.0` versions do not need a coordinated public
  release version.
- `packaging/oci/Dockerfile` accepts `0.0.0` only as a defensive build-argument
  default. The release builder passes the root product version explicitly.
- Local and external runtime constructors use `0.0.0` only when an embedding
  caller omits service metadata. The CLI passes the root package version.
- Test fixtures use `0.0.0` as inert client metadata.
- Every `0.0.0.0` value is a network bind address, not a version placeholder.
- Owner-controlled historical product specifications still name the original
  adapter packages. This release pass does not rewrite `project/spec/*.md`
  prose.

## What the current package tests prove

### Portable Node package

`pnpm test:local-package` builds the real archive, verifies its adjacent
manifest and SHA-256, and extracts it into two independent temporary install
directories. It proves:

- the `artifactserver` launcher reports the packaged version;
- production dependencies are bundled without symlinks or native `.node`
  extensions;
- source, tests, TypeScript, tsx, Vitest, Oxlint, declaration files, and the
  retired web entry point are absent;
- the canonical Review application and static assets ship;
- CLI help, local MCP onboarding, local server startup, publication, content
  serving, replacement, backup copy, restore, and preserved artifact identity
  work from the extracted archive;
- secrets do not appear in the exercised output surfaces; and
- the package works without network access during the runtime portion of the
  test.

The archive is therefore self-contained for its declared Node.js runtime. Its
release package metadata points `artifactserver` at the packaged Unix launcher;
the archive also contains a Windows command launcher.

### OCI image

`pnpm package:oci` and `pnpm verify:oci-image` prove:

- a multi-platform OCI index contains `linux/amd64` and `linux/arm64` images;
- per-platform SPDX and SLSA BuildKit attestations are present and reference
  released manifests;
- OCI blob digests, revision, version, entry point, working directory, fixed
  non-root user, and source-tree status match the requested build;
- the runtime filesystem is read-only and excludes source, tests, and
  development tools;
- compact SQLite/filesystem and external Postgres/S3 modes initialize, publish,
  serve, replace containers, and preserve committed data; and
- the support manifest remains secret-free.

## What is not yet proved

The current tests begin from a source checkout. They do not prove the final
consumer path:

- download assets from a GitHub Release without checking out the repository;
- verify `SHA256SUMS` and GitHub build provenance before installation;
- put the portable launcher on `PATH` on a clean Ubuntu and macOS runner;
- pull the published OCI image from GHCR by immutable digest;
- install each adapter from the public npm registry into a scratch project and
  load its declared entry point; or
- connect every released asset to one annotated `v0.1.0` tag and GitHub
  pre-release.

The release and install-verification workflows are the required proof for these
gaps.

## Release risks to resolve before tagging

1. Establish one version contract across the root package, adapters, MCP and
   channel metadata, Helm chart, tag, and workflow input.
2. Rename all public adapters to the owned `@plannotator` scope and update every
   shipping reference without changing owner-controlled spec prose.
3. Replace placeholder OCI and source coordinates with the Plannotator GitHub
   organization.
4. Replace the Pi adapter's wildcard `typebox` peer range with a tested bounded
   range.
5. Run `pnpm audit --prod` and either remove production blockers or record an
   exact, time-bounded exception.
6. Ensure release jobs do not restore or persist dependency/build caches.
7. Validate adapter tarball contents and entry points before npm publication.
8. Add checksum, SPDX SBOM, GitHub provenance, clean-install, and registry
   verification before creating the pre-release.

`pnpm audit --prod` reported no vulnerabilities across 1,481 production
dependencies on 2026-08-27. No audit exception is required for `v0.1.0`.
